The stack

ConcernChoiceWhy
Repositorypnpm workspaces + TurborepoCached task execution with minimal configuration. Strict resolution rules out phantom dependencies across shared packages.
Web appsVite + React 19 + TanStack Router, SPAAuthenticated internal apps have no server-rendering need, so no per-app server runtime. Routes and search params are typed end to end.

Server stateTanStack QueryCaching, revalidation and deduplication. Queries, keys and invalidation are organised by API resource, not by feature.
URL stateTanStack Router search paramsFilters, tabs, pagination and selection live in the URL: typed, validated, shareable.
Client stateZustand, feature-scopedSmall and unopinionated. Stores come from factories, never module singletons.

Repository structure

apps/
  web/
    console/          Vite + TanStack Router SPA
    admin/
  extensions/
    tray/             WXT
    clipper/
packages/
  api/                queries, mutations, keys shared by more than one app, by resource
  features/           screens and components shared by more than one app
  ui/                 tokens, primitives, patterns, forms
  contracts/          Zod schemas, the API boundary
  platform/           http, auth, extension, telemetry, flags, result, utils
  testing/            MSW handlers, fixtures
services/
  mock-api/           local API for development and tests
tooling/              tsconfig, eslint, tailwind preset, vite preset

Apps are grouped by surface because build tooling, release cadence and CI differ; each extension is its own distribution unit. Subfolders become separate packages only when a boundary needs enforcing.

Inside an application

apps/web/console/src/
  routes/             file-based route tree, thin
  api/
    tasks.ts          queries, mutations, keys
    lists.ts
    comments.ts
  modules/            features: screens, components, UI state
    tasks/
      components/
      model/          types, mapping, logic
  app/                providers, router, error boundaries
  lib/                app-local instances (session, API client) and helpers

Modules are owned by the app and may import one another freely; routes stay thin and compose them. api/ mirrors contracts/, one file per resource. Anything a second app needs moves to packages/api or packages/features, with app-specific parts injected by the host.

Dependency rules

app        →  features, api, ui, contracts, platform
features   →  api, ui, contracts, platform
api        →  contracts, platform
ui         →  platform                 (tokens and utilities only)
contracts  →  platform                 (result and utils only)
platform   →  nothing internal

Rules are checked twice: on package manifests, and by lint rules on imports. A ui component may not know about contracts, transport or auth. Packages expose subpath exports rather than one barrel, keeping builds incremental and tree-shaking honest.

Extension constraints

Extensions run as separate programs with no shared window, no ambient cookies and a delayed release cycle. Shared code is designed around that:

  • Transport-agnostic HTTP client. fetch and the token provider are injected, so one client runs in web apps and extension workers.
  • Auth as core plus adapters. Refresh and expiry logic is shared; token storage is per surface.
  • Shadow-root-safe UI. Content scripts render inside a shadow root, so primitives must attach portals (dialogs, menus, tooltips) there, not to document.body.
  • Service worker as trust boundary. Network calls and privileged actions run in the worker; other contexts request them by message.
  • API tolerates older extension clients. Store review delays extension releases, so API changes must stay backward compatible.

State model

KindOwnerShape
Server stateTanStack QueryMost of what gets called state. Apps reading the same resource cache it independently; we standardise keys and the fetch layer, not a runtime. Caches are per user and cleared on logout.
SessionAuth layerHandled at the auth boundary; cross-surface behaviour depends on the open auth decision.
Client UI stateZustandPer app, per feature. Sharing it across deployed apps would couple their releases.

Anything the URL can own lives in search params. Nothing Query owns belongs in Zustand, and nothing the URL should own belongs in either.

Open: the authentication approach and identity provider are not yet decided. The core/adapter split keeps that choice contained to the auth layer.

Open: internationalisation approach and tooling are not yet decided. Shared ui components already take all user-facing text as props, so any approach can be adopted without changing them.

Architecture proposal. Revisit when cached CI runs pass fifteen minutes, the package count passes twenty-five, or a second team joins the repository.
